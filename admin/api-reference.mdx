# API Reference

All admin endpoints are mounted under `/admin/system/` and require a valid admin session JWT (`role === 'admin'`, tier `Admin`). Each endpoint additionally requires a specific permission resolved from the caller's admin role in ADMIN\_DB.

The full surface is published in the live OpenAPI spec at `GET /api/openapi.json` (and the Scalar UI at `/docs`) under the **Admin System** tag, and cataloged in the machine-readable manifest `docs/admin/admin-manifest.json` (regenerate with `deno task admin:manifest`). Both are derived from a single source (`worker/routes/admin-system.openapi.ts`), and CI fails if a mounted admin route is missing from either — so the panel, API, and docs stay in lockstep (epic · G).

**Base URL**: `https://your-worker.workers.dev`

**Authentication**: All requests require `Authorization: Bearer <token>`.

**API keys**: admin operations are also reachable with a `blq_` API key, but access is **opt-in** — the key must carry the `admin` scope (a key owned by an admin without that scope is rejected with `403 "API key missing required scope: admin"`). Keys are a permissioned, audited alternative to a session, not a bypass; destructive operations still additionally require Cloudflare Access.

## Configuration Import / Export

The entire runtime-editable configuration — tiers, scopes, endpoint auth
overrides, announcements, admin roles, user groups, and API groups — can be
exported as a single bundle, edited offline, and re-imported. `ADMIN_DB` is the
source of truth; a bundle is a point-in-time snapshot that round-trips
(export → edit → import) to reproduce configuration. Bundles serialize to
**JSON**, **YAML**, or **TOML** (select with `?format=`; TOML omits null-valued
fields since it has no null literal).

### Export Config

```
GET /admin/system/config/export?format=json
```

**Permission**: `config:read`

Streams the bundle as a file download (`Content-Disposition: attachment`).
`format` is one of `json` (default), `yaml`, `toml`.

```bash
curl "/admin/system/config/export?format=yaml" \
  -H "Authorization: Bearer $JWT" -o bloqr-admin-config.yaml
```

### Import Config (dry-run + apply)

```
POST /admin/system/config/import?format=json[&dryRun=false]
```

**Permission**: `config:write`

The request body is the serialized bundle (content matching `format`). By
default this is a **dry run** returning a per-section diff (`added` / `removed` /
`changed` / `unchanged`) against the live config — nothing is written:

```json
{ "success": true, "dryRun": true, "diff": { "tiers": { "added": ["pro"], "removed": [], "changed": ["free"], "unchanged": 0 }, "...": {} } }
```

Add `?dryRun=false` to **apply**. Before writing, the current config is captured
as a snapshot (so the change can be reverted), then every section is upserted by
its natural key (create when absent, update when present). Volatile columns
(`id`, `created_at`, `updated_at`) are ignored. A malformed bundle is rejected
with `422` and **no** writes occur.

> **Defense-in-depth** — applying a bundle (and reverting, below) rewrites the
> whole config, so when Cloudflare Access is configured these ops additionally
> require a valid `CF-Access-JWT-Assertion` on top of `config:write` (`403`
> otherwise). Dry-run previews are exempt. In deployments without CF Access this
> check no-ops.

```json
{ "success": true, "dryRun": false, "snapshotId": 42, "applied": { "tiers": { "created": ["pro"], "updated": ["free"], "failed": [] }, "...": {} } }
```

```bash
curl -X POST "/admin/system/config/import?format=json&dryRun=false" \
  -H "Authorization: Bearer $JWT" -H "Content-Type: application/json" \
  --data-binary @bloqr-admin-config.json
```

The natural keys are: `tier_name` (tiers), `scope_name` (scopes),
`path_pattern` \+ `method` (endpoints), `id` (announcements), `role_name`
(roles), `group_name` (groups and api-groups).

### List Snapshots

```
GET /admin/system/config/snapshots
```

**Permission**: `config:read`

Returns snapshot metadata (id, `created_at`, `created_by`, `reason`), newest
first. Bundle bodies are omitted.

### Get Snapshot

```
GET /admin/system/config/snapshots/:id
```

**Permission**: `config:read`

Returns a single snapshot with its full bundle. `404` if not found.

### Revert to Snapshot

```
POST /admin/system/config/snapshots/:id/revert
```

**Permission**: `config:write`

Applies the snapshot's bundle. The current config is itself snapshotted first
(`reason: pre-revert:<id>`) so the revert can be undone. Returns the apply
report plus `preRevertSnapshotId`.

```bash
curl -X POST "/admin/system/config/snapshots/42/revert" \
  -H "Authorization: Bearer $JWT"
```

## Data-Subject Export (GDPR)

### Export a User's Admin Data

```
GET /admin/system/users/:userId/data-export
```

**Permission**: `users:read`

Aggregates everything the **admin subsystem** (`ADMIN_DB`) holds about a single
user — role assignments, group memberships, and the audit trail of actions they
performed — into one bundle, plus a `data_locations` manifest (store + table +
row count) answering "where does this user's data reside?". Read-only; the export itself is audit-logged (`user.data_export`). Audit rows are paged in and
capped, with `audit_log_truncated` set when older entries are omitted.

This covers the admin-domain slice only; the user's primary profile,
subscription, and API-usage records live in the application database and are
exported by that subsystem (see the `notes` field in the response).

```json
{
  "success": true,
  "export": {
    "user_id": "user_123",
    "exported_at": "2026-07-13T…",
    "data_locations": [
      { "store": "ADMIN_DB", "table": "admin_role_assignments", "record_count": 1, "description": "…" },
      { "store": "ADMIN_DB", "table": "admin_group_members", "record_count": 2, "description": "…" },
      { "store": "ADMIN_DB", "table": "admin_audit_logs", "record_count": 37, "description": "…" }
    ],
    "role_assignments": [ … ],
    "group_memberships": [ … ],
    "audit_log_entries": [ … ],
    "audit_log_truncated": false,
    "notes": [ … ]
  }
}
```

```bash
curl "/admin/system/users/user_123/data-export" \
  -H "Authorization: Bearer $JWT" -o user_123-admin-data.json
```

### Erase a User's Admin Data (delete-or-explain)

```
POST /admin/system/users/:userId/data-erase
```

**Permission**: `users:manage` — **plus Cloudflare Access** (destructive
defense-in-depth) when CF Access is configured.

Removes the **erasable** admin-domain data for the user — role assignments and
group memberships — and **explains** what is deliberately retained. The audit
log (`admin_audit_logs`) is append-only and kept for security / accountability /
legal compliance, so it is reported under `retained`, not deleted. The erasure
is itself audit-logged (`user.data_erase`) and the user's role-cache entry is
invalidated.

```json
{
  "success": true,
  "erasure": {
    "user_id": "user_123",
    "erased_at": "2026-07-13T…",
    "deleted": { "role_assignments": 1, "group_memberships": 2 },
    "retained": [
      { "store": "ADMIN_DB", "table": "admin_audit_logs", "record_count": 37, "reason": "Audit log is append-only and retained …" }
    ],
    "notes": [ … ]
  }
}
```

The user's primary profile, subscription, and usage records live in the
application database and are erased by that subsystem.

## Feature Flags

Feature flags are managed via [Cloudflare Flagship](/admin/feature-flags). These routes are a thin
proxy over the Flagship management API (`worker/handlers/admin-flagship.ts`) and return `503` if
`CF_ACCOUNT_ID`, `FLAGSHIP_APP_ID`, or `FLAGSHIP_API_TOKEN` aren't configured. Flag *evaluation*
inside the Worker does not use these routes — see the `[[flagship]]` binding.

### List Flags

```
GET /admin/config/feature-flags
```

**Permission**: `admin:read`

**Response** `200`:

```json
{
  "success": true,
  "total": 1,
  "items": [
    {
      "key": "new-parser-v2",
      "enabled": true,
      "default_variation": "off",
      "variations": { "off": false, "on": true },
      "rules": [
        {
          "conditions": [{ "attribute": "plan", "operator": "in", "value": ["pro", "admin"] }],
          "priority": 0,
          "serve_variation": "on",
          "rollout": { "percentage": 25 }
        }
      ],
      "description": "New AGTree v2 parser",
      "type": "boolean",
      "updated_at": "2026-06-24T10:30:00Z",
      "updated_by": "admin@bloqr.dev"

```

### Create Flag

```
POST /admin/config/feature-flags
```

**Permission**: `flags:write`

**Request Body**:

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `key` | string | ✅ | Unique flag identifier (letters, numbers, hyphens, underscores) |
| `enabled` | boolean |  | Default: `false` |
| `default_variation` | string | ✅ | Variation served when no rule matches or the flag is disabled |

```bash
curl -X POST https://api.bloqr.dev/admin/config/feature-flags \

  -d '{
    "key": "streaming-api-beta",
    "enabled": true,
    "default_variation": "off",
    "variations": { "off": false, "on": true },
    "rules": [{ "conditions": [], "priority": 0, "serve_variation": "on", "rollout": { "percentage": 10 } }],
    "description": "Server-sent events streaming API"
  }'
```

---

### Update Flag

```
PATCH /admin/config/feature-flags/:key
```

**Permission**: `flags:write`

**Path Parameters**: `key` — Flag key (string)

**Request Body**: Same fields as create (minus `key`), all optional — only the provided fields
change. Reads the current definition first and merges your payload on top of it, since Flagship's
own update endpoint replaces the entire flag; this means a plain `{"enabled": false}` toggle never
wipes out existing rules or variations.

---

### Delete Flag

```
DELETE /admin/config/feature-flags/:key
```

**Permission**: `flags:write`

Permanently deletes the flag. Cannot be undone.

## Local Auth Users

CRUD endpoints for managing local JWT auth users. These endpoints are available when the Worker is configured with a D1 `DB` binding and `JWT_SECRET`. They mirror [Clerk's Backend API](https://clerk.com/docs/reference/backend-api) for easy migration.

**Authentication required**: Admin tier + `admin` role (enforced by `checkRoutePermission`).

> **Note**: Password hashes are never returned. The `api_disabled` flag can be toggled to block a user's API access without deleting the account.

---

### List Local Auth Users

```
GET /admin/local-users
```

**Query Parameters**:

| Parameter | Type | Default | Description |
| --- | --- | --- | --- |
| `limit` | integer | 50 | Max results per page (1–100) |
| `offset` | integer | 0 | Pagination offset |

**Response**:

```json
{
  "success": true,
  "users": [
    {
      "id": "uuid",
      "identifier": "user@example.com",
      "identifier_type": "email",
      "role": "user",
      "tier": "free",
      "api_disabled": 0,
      "created_at": "2025-01-01T00:00:00Z",
      "updated_at": "2025-01-01T00:00:00Z"
    }
  ],
  "total": 42,
  "limit": 50,
  "offset": 0
}
```

---

### Get Local Auth User

```
GET /admin/local-users/:id
```

**Path Parameters**: `id` — User UUID

**Response**: `{ "success": true, "user": { ... } }` — same user object shape as the list items above.

---

### Create Local Auth User

```
POST /admin/local-users
```

**Request Body**:

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `identifier` | string | ✅ | Email or phone number |
| `password` | string | ✅ | Plaintext password (hashed server-side with PBKDF2) |
| `role` | string |  | `user` or `admin` (default: `user`) |
| `tier` | string |  | Override tier; defaults to the role's default tier |

**Response**: `201` with the created user object.

**Errors**:

- `409 Conflict` — identifier already registered

---

### Update Local Auth User

```
PATCH /admin/local-users/:id
```

**Request Body** (at least one field required):

| Field | Type | Description |
| --- | --- | --- |
| `role` | string | New role (`user` or `admin`) |
| `tier` | string | New tier (`free`, `pro`, `admin`) |
| `api_disabled` | `0` \| `1` | `1` blocks all API access for this user |

> Tier and role are independent. Setting `role` without `tier` auto-derives the default tier for that role. Setting both allows overrides (e.g. `{ "role": "user", "tier": "pro" }` for a Pro-rate-limited non-admin user).

**Response**: Updated user object.

---

### Delete Local Auth User

```
DELETE /admin/local-users/:id
```

**Response**: `{ "success": true, "message": "User deleted" }`

**Errors**:

- `404 Not Found` — user does not exist
