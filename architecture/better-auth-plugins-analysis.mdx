# Better Auth Plugins Analysis & Recommendations

<Callout kind="info">
  <strong>Superseded (2026-07-10)</strong>

  Most of the "Recommended"/"Under Consideration" verdicts
  below are now out of date — `organization()`, `haveIBeenPwned()`, `lastLoginMethod()`,
  `oneTimeToken()`, `jwt()`, `deviceAuthorization()`, and (feature-flagged) `apiKey()`,
  `mcp()`, `oidcProvider()`, `sso()`, `scim()`, `passkey()`, `captcha()` are now wired
  into `worker/lib/auth.ts`. **Treat the module-level JSDoc at the top of
  [`worker/lib/auth.ts`](https://github.com/bloqr-systems/bloqr-compiler/blob/main/worker/lib/auth.ts) as the single source of truth for
  current plugin status** — it can't drift out of sync with the code the way this
  analysis document can. The sections below are kept for their original
  cost/benefit/ZTA reasoning, but their Status/Recommendation lines predate the
  current implementation. See each plugin's `isXEnabled()`/`buildXOptions()` JSDoc in
  auth.ts for the up-to-date rationale, including why `apiKey()` is a deliberately
  separate system from the custom implementation described below, and why `stripe()`
  is installed but never mounted.

  For task-oriented "how do I enable X" instructions — env vars, endpoints exposed,
  schema, and rollout gotchas — see the
  [Plugin Extension Pack](/auth/plugin-extension-pack) guide.
</Callout>

## Executive Summary

This document provides a comprehensive analysis of Better Auth plugins for the bloqr-backend project, evaluating their implementation status, benefits, and recommendations for adoption.

<strong>Status at a Glance (superseded — see callout above):</strong>

- ✅ <strong>4 plugins already active:</strong> `bearer`, `twoFactor`, `multiSession`, `admin`
- 🔄 <strong>1 plugin recommended for implementation:</strong> `organization`
- 📋 <strong>6 plugins under consideration:</strong> `apiKey`, `magicLink`, `username`, `jwt`, `hibp`, `captcha`, `openAPI`

## Currently Implemented Plugins

### ✅ bearer() Plugin

<strong>Status:</strong> Active (auth.ts:175)

<strong>Purpose:</strong> Enables API authentication via `Authorization: Bearer <token>` header instead of browser cookies.

<strong>Endpoints Auto-Exposed:</strong>

- Session token endpoint returns `session.token` in responses

<strong>Usage:</strong>

- Frontend: `getToken()` method retrieves session token for API calls
- Critical for API-first architecture
- Enables Postman/curl access with tokens

<strong>Benefits:</strong>

- ✅ Essential for our API-centric architecture
- ✅ Already integrated with middleware/auth.ts
- ✅ Frontend service has `getToken()` method

<strong>Database Schema:</strong> Uses existing `Session.token` field

<strong>ZTA Compliance:</strong> ✅ Fully compliant - tokens verified via Better Auth

---

### ✅ twoFactor() Plugin

<strong>Status:</strong> Active (auth.ts:180)

<strong>Purpose:</strong> TOTP-based two-factor authentication for enhanced account security.

<strong>Configuration:</strong>

```typescript
twoFactor({
    issuer: 'bloqr-backend'
})
```

<strong>Endpoints Auto-Exposed:</strong>

- `POST /api/auth/two-factor/enable` \- Generate TOTP secret + QR URI
- `POST /api/auth/two-factor/verify` \- Verify TOTP code (enables 2FA)
- `POST /api/auth/two-factor/disable` \- Remove 2FA

<strong>Database Schema:</strong>

```prisma
model TwoFactor {
  id          String @id @default(uuid())
  userId      String @unique
  secret      String  // Encrypted TOTP secret
  backupCodes String  // JSON array
}

// User model field:
twoFactorEnabled Boolean @default(false)
```

<strong>Frontend Integration:</strong>

```typescript
enableTwoFactor(password)     // Get TOTP URI for QR
verifyTwoFactor(code)         // Verify code
disableTwoFactor(password)    // Disable 2FA
```

<strong>Benefits:</strong>

- ✅ Critical security feature for list/rule managers
- ✅ Easy user adoption (QR code scanning)
- ✅ Backup codes for recovery
- ✅ No additional dependencies

<strong>Recommendation:</strong> ✅ Keep active - essential security feature

### ✅ multiSession() Plugin

<strong>Status:</strong> Active (auth.ts:187)

<strong>Purpose:</strong> Multiple active sessions per user across devices.

<strong>Endpoints Auto-Exposed:</strong>

- `GET /api/auth/list-sessions` \- List all active sessions
- `POST /api/auth/revoke-session` \- Revoke specific session
- `POST /api/auth/revoke-other-sessions` \- Revoke all except current

<strong>Database Schema:</strong> Uses existing `Session` model with tracking

<strong>Frontend Integration:</strong>

```typescript
listSessions()              // Get all active sessions
revokeSession(token)        // Logout specific session
revokeOtherSessions()       // Logout all other devices
```

<strong>Benefits:</strong>

- ✅ Users can manage active devices
- ✅ Security: logout stolen/lost devices
- ✅ UX: see where you're logged in

<strong>Recommendation:</strong> ✅ Keep active - valuable security & UX feature

<strong>Recommendation:</strong> ✅ Keep active - critical for administration

## Recommended for Implementation

### 🔄 organization() Plugin

<strong>Status:</strong> Not implemented (commented at auth.ts:198)

<strong>Purpose:</strong> Multi-tenancy support - enables teams/organizations with member roles and permissions.

<strong>Use Cases for Our Project:</strong>

- Team-based compilation workflows
- Shared filter list ownership
- Organization-level API keys
- Multi-team list moderation

<strong>Endpoints Auto-Exposed:</strong>

- `POST /api/auth/organization/create` \- Create organization
- `POST /api/auth/organization/invite-member` \- Invite user to org
- `POST /api/auth/organization/remove-member` \- Remove member
- `POST /api/auth/organization/update-member-role` \- Change member role
- `GET /api/auth/organization/list-organizations` \- List user's orgs
- `GET /api/auth/organization/get-full-organization` \- Get org details

<strong>Database Schema Required:</strong>

```prisma
model Organization {
  id          String   @id @default(uuid())
  name        String
  slug        String   @unique
  logo        String?
  createdAt   DateTime @default(now())
  metadata    Json?

  members     Member[]
}

model Member {
  id             String       @id @default(uuid())
  organizationId String
  userId         String
  role           String       // owner | admin | member
  createdAt      DateTime     @default(now())

  organization   Organization @relation(fields: [organizationId], references: [id])
  user           User         @relation(fields: [userId], references: [id])

  @@unique([organizationId, userId])
}
```

<strong>Configuration:</strong>

```typescript
organization({
  allowUserToCreateOrganization: true,  // All users can create orgs
  organizationLimit: 3,                  // Max 3 orgs per user
})
```

<strong>Benefits:</strong>

- ✅ Native multi-tenancy support
- ✅ Built-in role system (owner/admin/member)
- ✅ Invitation workflow included
- ✅ Scales with business needs

<strong>Implementation Complexity:</strong> Medium

- Database migration required
- Frontend service updates needed
- Optional: Update FilterSource.ownerUserId to support org ownership

<strong>Recommendation:</strong> ✅ **IMPLEMENT** \- High value for collaborative use cases

## Plugins Under Consideration

### 📋 apiKey() Plugin (Custom vs. Built-in)

<strong>Status:</strong> Custom implementation active at `worker/handlers/api-keys.ts`

<strong>Better Auth Plugin:</strong> Provides standardized API key management at `/api/auth/admin/api-keys/*`

<strong>Current Custom Implementation:</strong>

```typescript
// worker/routes/api-keys.routes.ts
POST   /api/keys         // Create key
GET    /api/keys         // List keys
DELETE /api/keys/:id     // Revoke key
PATCH  /api/keys/:id     // Update key
```

<strong>Database Schema:</strong>

```prisma
model ApiKey {
  id                 String    @id @default(uuid())
  userId             String
  keyHash            String    @unique
  keyPrefix          String    // Display prefix
  name               String
  scopes             String[]  @default(["compile"])
  rateLimitPerMinute Int       @default(60)
  lastUsedAt         DateTime?
  expiresAt          DateTime?
  revokedAt          DateTime?
}
```

<strong>Custom Features:</strong>

- ✅ Per-key scopes (`compile`, `admin`, etc.)
- ✅ Per-key rate limits
- ✅ Expiration management
- ✅ Last used tracking

<strong>Better Auth apiKey() Plugin Features:</strong>

- Standard API key CRUD
- Simpler implementation
- Less customization

<strong>Analysis:</strong>

- Our custom implementation has richer features (scopes, per-key limits)
- Better Auth plugin would simplify maintenance
- Migration would require schema changes

<strong>Recommendation:</strong> ⚠️ **KEEP CUSTOM** \- Our implementation is more feature-rich

- Optional: Add Better Auth plugin for secondary API key type (read-only tokens)

### 📋 jwt() Plugin

<strong>Status:</strong> Not needed (bearer plugin sufficient)

<strong>Purpose:</strong> Stateless JWT tokens for API authentication.

<strong>Current Solution:</strong> `bearer()` plugin already provides token-based auth

<strong>Analysis:</strong>

- bearer() uses session tokens (validated via database)
- jwt() uses stateless tokens (signed, no DB lookup)
- Trade-offs:

  - bearer: Can revoke immediately (session deletion)
  - jwt: Faster (no DB lookup), but can't revoke until expiry

<strong>Recommendation:</strong> ❌ **NOT NEEDED** \- bearer() plugin is sufficient

- Our ZTA architecture requires database-validated tokens
- Immediate revocation is critical for security

---

## ZTA Compliance Notes

All Better Auth endpoints must comply with Zero Trust Architecture:

### Endpoint Security Requirements

- <strong>Edge Layer:</strong> WAF/API Shield in sync with OpenAPI spec, CORS allowlist
- <strong>Worker Layer:</strong> Auth chain before business logic, rate limiting on all endpoints
- <strong>Validation:</strong> Zod schemas at trust boundaries
- <strong>Telemetry:</strong> Security events for auth failures

### Plugin-Specific ZTA

- `organization()`: Membership checks before org operations
- `magicLink()`: Token expiry validation (default: 5 minutes)
- `hibp()`: No PII sent to external API (k-anonymity)

## Frontend Integration Guide

### Adding Organization Support

**Step 1: Extend BetterAuthService**

```typescript
// frontend/src/app/services/better-auth.service.ts

async createOrganization(name: string, slug: string): Promise<void> {
  const res = await fetch(`${this.apiBaseUrl}/auth/organization/create`, {
    method: 'POST',
    credentials: 'include',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ name, slug })
  });
  if (!res.ok) throw new Error('Failed to create organization');
}

async listOrganizations(): Promise<Organization[]> {
  const res = await fetch(`${this.apiBaseUrl}/auth/organization/list-organizations`, {
    credentials: 'include'
  });
  if (!res.ok) throw new Error('Failed to list organizations');
  return await res.json();
}
```

  async updateMemberRole(orgId: string, userId: string, role: string) { ... }
